# Northwind Store

![Demo App](/frontend/public/screenshot-for-readme.png)

Northwind Store is a full-stack e-commerce application for browsing products, managing a cart, checking out, and following up on orders. It combines a React storefront with a TypeScript/Express API and PostgreSQL, with Clerk authentication and integrations for Polar payments, Stream support, and ImageKit media.

## 🧩 Implementation details

### Application structure

- **Storefront:** The React single-page app uses Vite, React Router, TanStack Query, Tailwind CSS, and DaisyUI. Pages and hooks separate the catalog, product details, cart, checkout return, orders, order support, and admin product workflows.
- **API:** An Express 5 API written in TypeScript serves the frontend and exposes the catalog, account, checkout, order, support, and administration endpoints. Zod schemas validate checkout and product input.
- **Persistence:** Drizzle ORM maps PostgreSQL tables for users, products, checkout sessions, orders, and order items. Prices are stored as integer cents; order items keep a copy of their unit price at purchase time.

### Authentication and account roles

Clerk provides frontend sign-in and backend request authentication. When an authenticated user first accesses an API feature that needs a local account, the backend fetches their user details from Clerk and creates a local `users` record. New local roles are initialized from Clerk public metadata and default to `customer`; existing local roles are preserved. Without a Clerk webhook, later profile changes and account deletions are not automatically synchronized to PostgreSQL. Local roles (`customer`, `support`, and `admin`) control access: admin routes require an admin role, while staff can view support orders and send video invitations.

### Catalog, cart, and checkout

The public product API returns active products and categories. The storefront keeps cart selections in its client-side cart store and uses the API to load current product details. Checkout requires a signed-in user and validates the submitted product IDs and quantities. The backend reloads active product prices from PostgreSQL and calculates the total itself rather than trusting prices supplied by the browser.

For a valid cart, the API stores a checkout session containing the selected product IDs, quantities, unit prices, and total, then creates a Polar checkout and returns its URL. Polar sends payment events to the backend webhook. The webhook verifies the signature and, for a paid order, creates the order and its line items in a database transaction before removing the checkout session. Duplicate paid events are handled idempotently.

### Orders and customer support

Customers can list their own orders and view order details; support and admin users can view orders across customers. Paid orders can open a Stream messaging channel for customer support. The API issues Stream user tokens only to authenticated users, and only support or admin users can send a video invitation for an order.

### Product administration and images

Admin-only endpoints create, edit, deactivate, and delete products. Product request bodies are validated on the server. Image uploads use short-lived ImageKit authentication parameters generated by the API; the browser uploads the image directly to ImageKit and saves its URL and file ID with the product. A product referenced by an order cannot be deleted, so it can be deactivated instead.

### Payment webhook and operational behavior

The Polar webhook route receives the raw request body required for signature verification. A missing Polar webhook secret returns a service-unavailable response, invalid webhook requests are rejected, and unexpected API errors return a generic server error. Clerk user provisioning no longer requires a webhook endpoint. The `/health` endpoint provides a basic API health check.

## 🧪 Environment Variables

### Backend (`/backend`)

```bash
PORT=<your_port>
NODE_ENV=<development_or_production>

DATABASE_URL=<your_postgresql_connection_string>

CLERK_PUBLISHABLE_KEY=<your_clerk_publishable_key>
CLERK_SECRET_KEY=<your_clerk_secret_key>

STREAM_API_KEY=<your_stream_api_key>
STREAM_API_SECRET=<your_stream_api_secret>

IMAGEKIT_PUBLIC_KEY=<your_imagekit_public_key>
IMAGEKIT_PRIVATE_KEY=<your_imagekit_private_key>
IMAGEKIT_URL_ENDPOINT=<your_imagekit_url_endpoint>

FRONTEND_URL=<your_frontend_url>

POLAR_ACCESS_TOKEN=<your_polar_access_token>
POLAR_WEBHOOK_SECRET=<your_polar_webhook_secret>
POLAR_API_BASE=<your_polar_api_base_url>

POLAR_CHECKOUT_PRODUCT_ID=<your_product_id>
```

### Frontend (`/frontend`)

```bash
VITE_CLERK_PUBLISHABLE_KEY=<your_clerk_publishable_key>
VITE_API_URL=<your_backend_api_url>
```

## ▶️ Run locally

1. Create `backend/.env` and `frontend/.env` using the variables above. Configure the external Clerk, PostgreSQL, Polar, Stream, and ImageKit services you plan to use.
2. Install dependencies and start the API:

   ```bash
   cd backend
   npm install
   npm run dev
   ```

3. In another terminal, install dependencies and start the storefront:

   ```bash
   cd frontend
   npm install
   npm run dev
   ```

The backend also provides `npm run build` and `npm start`; the frontend provides `npm run build` and `npm run lint`.
